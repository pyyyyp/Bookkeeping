# REQ-008 坏数据不是死路

- 状态: 待实现
- 优先级: P1
- 上下文: Ledger
- 提出: 2026-10-03
- 前置: `REQ-006`（它让坏数据**可见**，但没给出路）、`ADR-0005`（条目可以物理删除）

## 用户故事

界面告诉我：「有 1 条记录读不出来（数据可能被外部改坏），已跳过；它们仍计入合计。」

我看懂了问题，**但没有任何办法处理**：那条钱一直算在我的支出里，而我在列表里
找不到它、点不开它、也删不掉它。这个提示变成了一个我无法消除的警告。

## 背景

`REQ-006` 修好的是"看不见"（跳过 + 计数 + 如实告知）。但它把用户留在了**死路**上：

- 那条数据的钱**仍计入合计与占比**（`REQ-006/BR-5`：钱是事实，坏掉的只是渲染）
  → 用户会看到一个**对不上**的总数：各分类之和比他的记忆多；
- 而它在列表里**不存在** → 无法定位、无法编辑（域校验根本读不出它）、无法删除。

`ADR-0005` 已经裁定「条目可以物理删除」（条目没有下游引用者）。所以
"删掉这条坏数据"**不是在制定新规则**，而是把已有规则用到这条路上。

## 范围

**做**

- 把坏行**列出来**：每行给出**原始标识**与**读不出来的原因**
- 逐条**物理删除**，删除前二次确认（删的是钱，且不可恢复）
- 删完立即刷新列表与合计

**不做**

- **导出**（"先抢救数据再删"是另一条路：需要定文件格式、位置、是否加密 —— 见下面的未决）
- **编辑**坏行（域校验读不出它，改不了；这不是省事，是不可能）
- **自动清理**（绝不能悄悄删用户的钱）

## 验收标准

### AC-1 看得到坏行

**给定** 库里有 1 条读不出来的行
**当** 用户点开「有 N 条读不出来」那个提示
**那么** 列出这 N 行，每行给出**原始标识**与**读不出来的原因**

### AC-2 删得掉

**当** 用户对其中一行确认删除
**那么** 它从坏行清单消失、计数减一，且数据库里那一行**物理消失**（不是打标记）

### AC-3 删完合计跟着变

**当** 那条坏数据被删掉
**那么** 合计与占比**立即**把它的钱扣掉 —— 它本来计入（`REQ-006/BR-5`），
删掉后就不该再算。这是"删干净了"的旁证，也是用户能看到的闭环。

### AC-4 删除要二次确认

**当** 用户点删除
**那么** 先要确认（与记账页的删除一致：删的是钱，没有撤销）

## 业务规则

- **BR-1 只删不改**：坏行读不出来就改不了 —— 域的校验说了算，不是界面省事。
- **BR-2 物理删除**：与条目一致（`ADR-0005`），不留墓碑、不加软删除字段。
- **BR-3 绝不自动清理**：坏数据只能由用户点掉。**悄悄删钱是这类功能里最不能犯的错** ——
  所以本需求连"启动时自动清一遍"都不做，哪怕它看起来更方便。
- **BR-4 原因要如实**：照实写域校验抛出的那句话（例如"标识不是合法 UUID"），
  不要翻译成"数据损坏"这类含糊说法。含糊的提示会把排障从一分钟变成一小时 ——
  这一条正是 `REQ-006` 教我的。
- **BR-5 顺序不能颠倒**：删除**之前**它的钱仍计入，删除**之后**才扣掉。
  反过来会出现"数字先变、行还在"的错觉。
- **BR-6 不记 PII**：原因里可以出现**原始标识**（那是用户自己库里那一行的键，
  也是唯一能指回它的东西），但不带金额、备注、分类名。

## 未决（本卡不做）

- **Q-021 坏数据要不要能导出？** 我的选择是**先做能删**：它是唯一能**恢复一致性**的最小动作
  （数字对得上），而导出的成本大得多（文件格式、存放位置、是否加密）。
  如果将来想"先抢救再删"，那是一个独立需求，会改这里的界面顺序。
