# REQ-007 分类下钻：这一类的钱花在哪

- 状态: 待实现
- 优先级: P1
- 上下文: Ledger + Insight（跨上下文，读路径）
- 提出: 2026-10-03
- 前置: `REQ-005`（分类占比）、`REQ-006`（出问题时看得见）

## 用户故事

占比告诉我「娱乐 ¥40000.00 99.9%」。我盯着这个数字的第一个反应是：
**这四万是哪些笔？** 现在唯一的办法是回到记账页，一条条往下翻，靠肉眼找。

## 背景

`REQ-005` 让「钱花在哪类」有了答案。但**分类是一个统计口径，不是一条记录** ——
用户看到聚合值之后，下一个问题必然是它的构成。这不是新功能，而是把已有的
【占比】和已有的【条目列表】接起来。

有一条已经存在的口径必须在这里守住：占比的金额是 SQL 里 `GROUP BY` 出来的
（`REQ-005/BR-5`）。如果下钻清单的口径与它不一致（比如换了时间字段、
或者把已归档的分类排除了），用户会看到**同一个分类两个数** ——
而这正是 `REQ-005/BR-2` 花力气避免的事。

## 范围

**做**

- 点「支出构成」里的一行 → 打开该分类**在该月**的条目清单（只读）
- 标题说清是哪个分类、哪个月（否则用户不知道自己在看什么）
- 该分类当月没有条目时说清楚（占比里有它但清单为空是可能的：金额来自已归档分类的条目）
- 关闭后回到原页面，**不改变任何状态**

**不做**

- 在清单里编辑/删除（v1 只读 —— 两条改动路径迟早不一致，见 `BR-3`）
- 该分类的合计/均值/趋势（那是另一个需求）
- 跨月的"这个分类一共花了多少"（本次只做**当月**，月份口径必须和占比一样）
- 按分类分页（条目上限沿用列表的 200 条）

## 验收标准

### AC-1 点占比里的一行，看到该分类在该月的条目清单

**给定** 当月「娱乐」有 2 笔（¥40000.00 与 ¥20.00）
**当** 用户点占比里的「娱乐」那一行
**那么** 弹出一份清单，**标题写清分类名与月份**，里面是这 2 笔（金额、发生日期）

### AC-2 清单里条目的金额之和 = 占比行显示的金额

**给定** 同一分类、同一月份
**当** 清单打开
**那么** 清单里各条金额之和**恰好等于**占比行上的那个数字（口径同源，见 `BR-1`）

### AC-3 该分类当月没有条目时说清楚

**给定** 该分类当月金额来自已归档分类的条目 / 或本来就为空
**当** 清单打开
**那么** 显示明确的空态文案，而不是一片空白

### AC-4 关闭后一切照旧

**当** 用户关闭清单
**那么** 合计、占比、记账列表**都没有变化**（只读操作不留痕）

## 业务规则

- **BR-1 口径与占比完全一致**：同一个分类、同一个**半开区间** `[start, end)`、
  同一个归属字段（`occurredAtEpochMilli` 发生时间）。两个数字会并排出现，
  口径不一致就是错的（沿用 `REQ-005/BR-5` 的推理）。
- **BR-2 已归档的分类也能下钻**：占比里有它（`REQ-005/BR-2`），清单就必须能打开它 ——
  否则用户点了一行却什么都没发生。
- **BR-3 v1 只读**：清单里不提供编辑/删除。理由不是"省事"，而是**改动路径只能有一条**
  （记账页那条），两条路径各写一套校验迟早漂移（`REQ-003` 的 `revise`/`record` 教训）。
- **BR-4 跨上下文只走内核契约**：Insight 需要告诉 Ledger「用户点了哪一行」，
  但它**不知道分类是什么**。所以内核的读模型带一个**不透明标识**，
  Insight 只是把它**原样回传**，绝不解释它（`ADR-0008` 的推理延续）。
- **BR-5 不新端口**：下钻要的数据（某个分类在某月的条目）住在 Ledger 内部，
  消费方与实现方是同一个上下文 —— 加端口只会凭空多一层。**新用例，不是新端口。**

## 影响面

- 内核：`CategoryAmount` 增加一个**不透明标识**字段（`BR-4`）
- Ledger：新增一条按分类 + 区间的查询、仓储方法、用例、ViewModel 与只读清单界面
- Insight：占比行变成可点，把（标识 + 月份）交给组合根
- 组合根 `:app`：持有"当前下钻的是哪一行"，并渲染 Ledger 的清单（R2 要求它来做这件事）
