# REQ-006 出问题时看得见

- 状态: 待实现（**阶段 B / C 已完成**；实现见 `T-015`）
- 上下文: Ledger（数据层）+ Insight（读模型）；横切面是**可诊断性**
- 提出: 用户（2026-10-03，「修复问题，然后按你推荐的来」）
- 关联: `ADR-0010`（日志抽象）、`REQ-002`/`REQ-005`（合计与占比的读路径）、`T-007` 卡里挂了三轮的已知缺口

## 用户故事

> 作为一个自己记账的人，
> 当应用说"出错了"时，我想知道**到底哪里错了**——
> 而不是看到一句笼统的提示，也不知道数据是不是还在。

## 背景：三个已经真实发生的问题

| # | 现象 | 根因 | 来源 |
|---|---|---|---|
| 1 | 只知道"本机数据库出错"，不知道是磁盘满、库损坏还是别的 | `Technical.Storage` 不带载荷，**异常原因从来没被记录**（项目一直没有日志抽象） | `T-007` 卡的已知缺口，挂了三轮 |
| 2 | **读**列表失败时，界面说的是「保存失败：本机数据库出错，**这笔没有记上**」 | 读与写**共用**一个 `SaveFailure.Storage`，文案只有一套 | `T-013` 冒烟时踩到 |
| 3 | 库里有一条 id 不是 UUID 的脏数据 → 界面**整张列表消失**（显示「还没有记账」） | `recent()` 里 `map { restore(...) }` 一处抛错，**整批**失败 | `T-013` 冒烟时踩到（教训 24） |

第三个尤其糟：**用户看到的是"没有账目"，而真实情况是"账目都在，只是有一条读不出来"** ——
那正是本项目最不能接受的失败形态（把"读不出来"伪装成"没有数据"）。

## 范围

**做**：

- 一个**最小**日志接口（`core:common` 的 `AppLogger`），把存储失败的原因记下来
- **读失败与写失败的提示分开**（文案各说各的事）
- 库里出现**读不出来的行**时：**跳过它、其余照常显示、并如实说明有几条读不出来**
- 三处的异常翻译统一走日志：条目的仓储、分类的仓储、跨上下文合计的读取器

**不做**：

- 不引入日志框架（Timber / Kermit / slf4j）：一个接口 + 一个 Android 实现足够，
  引入框架要付依赖、初始化、混淆规则的成本，而当前只有一个消费者
- 不做日志落盘 / 上报 / 崩溃收集
- 不做"修复脏数据"的界面（那是另一件事，且要新的裁决）
- 不改合计口径（见 `BR-5`）

## 验收标准

> 业务语言。⚠️ 格式必须是 `### AC-n <标题>`（追溯脚本按这个模式抓取）。

### AC-1 保存或读取失败时，原因被记录在日志里

```
Given 本机数据库写入失败（例如磁盘满）
When  保存这笔账目
Then  用户仍然看到"保存失败"的提示
      同时日志里能找到这次失败的**原因**（异常类型与消息）
      而日志里**没有**金额、备注、分类名这类隐私内容
```

### AC-2 读取失败与保存失败的提示不一样

```
Given 列表读取失败（而不是保存失败）
When  我打开记账页
Then  提示说的是"账目暂时读不出来"这类**读**失败的话
      而不是"这笔没有记上"（那句话会让我以为是我刚才那次保存出了问题）
```

### AC-3 一条读不出来的数据不会让整张列表消失

```
Given 库里有 5 条账目，其中 1 条的数据被外部改坏了（例如 id 不是合法 UUID）
When  我打开记账页
Then  另外 4 条**照常显示**
      并且明确告诉我"有 1 条记录读不出来"（不是静默丢掉，也不是整张空白）
```

## 业务规则

| 编号 | 规则 | 理由 |
|---|---|---|
| `BR-1` | 日志走**项目自己的最小接口**（`AppLogger`），不引入日志框架 | 当前只有一个消费者；框架带来的依赖与初始化成本换不来什么。接口小到可以随时替换实现 |
| `BR-2` | 日志**不含 PII**：只记固定文案 + 异常类型/消息，**不记金额、备注、分类名** | AGENTS.md 第 7 节第 13 条。异常消息本身可能含 SQL 片段，但那不含用户数据 |
| `BR-3` | **读失败与写失败是两种失败**，界面文案必须分开 | 说错方向的提示会让用户排查错地方（`AC-2`） |
| `BR-4` | 读不出来的行：**跳过 + 计数 + 明确告知**，既不静默丢弃，也不让整批失败 | `AC-3`。静默丢弃等于把"数据坏了"伪装成"数据少了"；整批失败则让一条坏数据藏起全部账目 |
| `BR-5` | **合计与占比的口径不变**：它们由 SQL 求和，坏行**仍计入金额** | 钱是事实（那一行确实存在），坏掉的只是"能不能把它渲染成条目"。二者不一致时，`AC-3` 的计数提示就是解释 |
| `BR-6` | 日志级别用 `warn`（可恢复的业务失败），不用 `error` | `error` 应当留给"应用自身出 bug"；存储失败是被处理过的已知路径 |
