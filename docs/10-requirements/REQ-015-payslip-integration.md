# REQ-015 出勤与工资单的集成

- 状态: 待实现
- 优先级: P1
- 上下文: Payroll（消费两个内核端口）
- 提出: 2026-10-03
- 前置: `REQ-012`（`DayType`）、`REQ-013`（日收入计算）、`REQ-014`（出勤事实）、`ADR-0012`（门槛归 Payroll）

## 用户故事

前三个需求各自都对了：日历知道"这天是什么日子"，工时知道"这天干了多久"，
薪资知道"这个日子 × 倍率 = 多少钱"。**但这个月我到底该拿多少，还是没人回答** ——
因为没有人把它们**合起来**。

## 背景

这条链路第一次真正接起来，而"接"的方式决定了三个坑：

1. **门槛放在哪**：`Q-017` 说"满 8 小时算 1 天"。放 Worklog 就得多一条到 Calendar 的边
   （它得知道哪天是休息日才能判"要不要算加班"）→ 按 `ADR-0012` 决策 2，**归 Payroll**
   （它本来就认识 Calendar）。
2. **没记录 ≠ 缺勤**（`Q-026`）：月薪制的默认含义是"该上班的日子都上了"。
   静默按缺勤处理会**悄悄扣钱**。
3. **当月还没过完**：未来那些天既没上班也没缺勤 —— 把它们当成"没出勤"是错的。

## 范围

**做**

- 一个用例把两个端口合起来：`Calendar`（哪天是什么日子）+ `Worklog`（每天多少分钟）
- 用门槛（`Q-017` v1：满 8 小时）判定休息日/法定节假日算不算加班
- 只算到"今天"为止
- 工资单上带上"节假日数据没填"这个事实

**不做**

- 工时**持久化**（Room 表 + 迁移）—— 单独一张卡
- 界面
- 半天加班（`Q-025`：需要有理数倍率）
- 缺勤标记（`Q-026`：v1 没有，所以缺勤分支只有测试覆盖）
- 选"这个月该用哪份月薪"（`Q-019` 的 `effectiveFrom` 已落字段，历史查询未做）

## 验收标准

### AC-1 工作日：不论有没有记录，都按 1×

**给定** 某工作日（没有缺勤标记）
**当** 算这一天的收入
**那么** `1 × 日薪` —— **没有记录也一样**（`Q-026`：没记录不等于缺勤）

### AC-2 休息日：够门槛 2×，不够 0

**给定** 某休息日，当天已确认工时 `≥ 8 小时` / `< 8 小时`
**那么** 分别是 `2 × 日薪` / `0`

### AC-3 法定节假日：够门槛 3×，不够仍带薪 1×

**给定** 某法定节假日，当天已确认工时 `≥ 8 小时` / `< 8 小时`
**那么** 分别是 `3 × 日薪` / **`1 × 日薪`**（`Q-015`：法定节假日休息带薪）

### AC-4 门槛是线的两边

**给定** 休息日当天 `7:59` / `8:00`
**那么** 分别是 `0` / `2 × 日薪` —— 差一分钟就是两个结果，所以边界要单独测

### AC-5 只算到「今天」为止

**给定** 当月还没过完
**当** 算这个月的工资单
**那么** 只包含 `≤ 今天` 的那些天 —— 未来的日子**既不算出勤也不算缺勤**
（把没到的日子当成"没出勤"会让工资单凭空少一截）

### AC-6 工资单要能说出「节假日数据没填」

**给定** 该月的日期类型里有一天来自"这一年还没有节假日数据"（`REQ-012/AC-4` 的 `missingYear`）
**那么** 工资单上带 `holidayDataMissing = true`
（否则用户会以为今年没有节假日 —— 而真相是数据没填。静默退化最糟）

## 业务规则

- **BR-1 门槛住 Payroll**（`ADR-0012` 决策 2）：它是**钱**的规则。
  Worklog 只给事实（多少分钟），Calendar 只给日期类型。
- **BR-2 两个端口都住内核**（`ADR-0008`）：`WorkCalendar`（`T-025`）与 `WorklogReader`（`T-027`）。
  Payroll **不认识**任何实现，也不认识 `feature:calendar` / `feature:worklog`。
- **BR-3 默认是"上班"**（`Q-026`）：月薪制的默认含义就是"该上班的日子都上了"。
  缺勤是例外，需要显式标记（v1 没有）。
- **BR-4 未来的日子不参与**：工资单不预支未来，也不把没到的日子当成缺勤。
- **BR-5 这个用例不会失败**：两个端口都是**同步纯查询**，而且各自已经把 IO 失败
  吞成了"没有数据 / 数据没填"（`ADR-0011` 决策 2 的同一原则）——
  所以这里没有可失败之处，返回 `Payslip` 而不是 `Outcome`。
  （将来若某个端口改成会失败，这个签名会跟着改 —— 那时是一次显式的改动。）
