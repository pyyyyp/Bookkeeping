# REQ-011 下钻清单里能改能删

- 状态: 待实现
- 优先级: P1
- 上下文: Ledger（**不新增跨上下文通路**）
- 提出: 2026-10-03
- 前置: `REQ-007`（下钻）、`REQ-003`（编辑）、`REQ-008`（删除与二次确认）
- 相关未决: `Q-023`（本需求形状的取舍）

## 用户故事

我点开「娱乐 ¥40000.00」，清单里看到那笔记错了日期。
现在我只能关掉它、滚动到记账页、在列表里**自己找**那一条 —— 而我刚刚明明已经指着它了。

## 背景与**真正**的取舍

`REQ-007` 当时把下钻做成**只读**，理由是 `BR-3`：**改动路径只能有一条**。
那条理由今天依然成立 —— `REQ-003`（编辑）与 `T-018`（坏数据删除）的教训都是
"两条路径各写一套校验/文案，迟早漂移"。

所以这个需求**不是**"在下钻里再加一套编辑表单"，而是：
**下钻里的「改/删」只是把这一条交给账本页那套流程。**

关键事实：下钻对话框本来就住在 `feature:ledger`（`T-017` 的决定），
所以这件事**不需要任何跨上下文的写通路** —— Insight 依旧只给一个不透明标识。

## 范围

**做**

- 下钻清单每一行给「改」「删」两个入口
- 点「改」：关掉下钻 → 打开**账本页那套**编辑表单，并且**已回填**这一条
- 点「删」：关掉下钻 → 弹出**账本页那套**二次确认（文案逐字相同）
- 改/删成功后，合计、占比、趋势一起刷新（沿用 `entriesRevision` 机制）

**不做**

- 在下钻里**另写**编辑表单或确认文案（这正是不做的事）
- 在下钻里改完**不关**对话框（一次只处理一件事：模态套模态容易点错层）
- 批量操作（"这个分类本月全删"）—— 那是另一个需求，而且危险得多

## 验收标准

### AC-1 每一行都有「改」和「删」

**给定** 下钻清单里有条目
**当** 用户看任意一行
**那么** 这一行有「改」和「删」两个入口（与账本页列表的措辞一致）

### AC-2 点「改」→ 编辑表单打开且已回填

**当** 用户在某一行点「改」
**那么** 下钻关掉，账本页的编辑表单打开，金额/方向/分类/发生日期/备注**都已回填**这一条的值

### AC-3 改完，合计与占比一起变

**当** 用户改完并保存
**那么** 合计、占比、趋势**立即**跟着变（不需要重启，也不需要手动刷新）

### AC-4 点「删」→ 同一套二次确认

**当** 用户在某一行点「删」
**那么** 弹出的确认文案与账本页那处**逐字相同**（`REQ-001` 的既有文案）；
点「取消」则数据库一字未改

### AC-5 删完，合计跟着变

**当** 用户确认删除
**那么** 那一行从下钻里消失（下次打开时不再出现），且合计、占比、趋势一起变

## 业务规则

- **BR-1 改动路径仍然只有一条**：下钻里的改/删是**打开账本页那套流程**，不是自己写数据。
  校验、二次确认、失败文案都只有一份（`REQ-003`/`T-018` 的教训）。
- **BR-2 不引入跨上下文的写通路**：下钻住在 `feature:ledger`，Insight 依旧只给不透明标识（`REQ-007/BR-4`）。
- **BR-3 一次只处理一件事**：点「改」或「删」先把下钻关掉，不让两个对话框叠在一起 ——
  这既避免点错层，也让"我改的是哪一条"始终只有一个答案。
- **BR-4 刷新靠既有信号**：`entriesRevision` +1 让组合根通知 Insight 重算（`T-013`/`T-018` 同一机制）。
  这是"合计不跟着变"那个真 bug 的修法，新入口必须走同一条路。

## 已知代价

这一条的自动化覆盖**只在既有测试里**（`LedgerViewModel` 的编辑/删除行为、`REQ-003`/`T-008` 的用例）。
新加的只是**接线**（哪个按钮调用哪个既有方法），而接线在 Compose 里没有 UI 测试框架 ——
所以本卡的证据以**真机冒烟**为主，且会把"确认文案只有一处"用 `grep` 核实（不重复实现）。
