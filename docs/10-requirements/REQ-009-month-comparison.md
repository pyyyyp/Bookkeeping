# REQ-009 月度环比：这个月比上个月多花了多少

- 状态: 待实现
- 优先级: P1
- 上下文: Insight（读模型）
- 提出: 2026-10-03
- 前置: `REQ-002`（本月合计）、`REQ-005`（占比）、`REQ-007`（下钻）

## 用户故事

合计告诉我「2026 年 10 月 支出 ¥40045.00」。第二个问题几乎是自动的：
**跟上个月比呢？** 我多花了还是少花了？现在只能自己点「上一月」把两个数记在心里做减法。

## 背景

`REQ-002` 已经有"某个月花了多少"，`REQ-005` 有"花在哪类"，`REQ-007` 有"这一类是哪几笔"。
**缺的是时间维度上的第一个对比**。而它出奇地便宜：跨上下文那个端口的方法就叫
`totalsIn(range)` —— 它收的是**任意区间**，所以上个月只是"同一件事换个区间"，
**不需要新端口、不需要新查询、不需要动 Ledger 一行代码**。

一条必须守住的规则：两个月的**区间口径**都要走内核的 `YearMonth.toTimeRange`
（`REQ-007` 时从 Insight 内部搬进内核的那个）—— 否则"环比"与"合计"会在月份边界上打架。

## 范围

**做**

- 在本月合计下面显示**支出的环比**：多花 / 少花 / 持平（带符号与金额）
- 上个月没有记账时，基线是 0（差额就是本月全额）—— **不显示成错误**
- 翻月时环比与合计**一起**变

**不做**

- 趋势图 / 多月折线（那是 `REQ-009` 之后的事，需要新的读模型：见候选 J）
- 收入与结余的环比（本月只做**支出** —— 它才是"我花得多了吗"的问题；加另外两个会让这块变成三行数字）
- 与**去年同期**对比（季节性是另一个问题，需要用户先有足够的历史数据）
- 分类级别的环比（占比区已经有构成，混进环比会让那块同时回答两个问题）

## 验收标准

### AC-1 合计下面显示与上月的支出差额

**给定** 本月支出 ¥40045.00、上月支出 ¥41000.00
**当** 用户打开该月
**那么** 合计下面显示「比上月少花 ¥955.00」（**方向与符号都正确**）

### AC-2 上月没有记账时基线是 0，且不是错误

**给定** 本月支出 ¥40045.00、上月一条记录都没有
**当** 用户打开该月
**那么** 显示「比上月多花 ¥40045.00」—— 基线是 0 这个事实**如实表达**，
而不是"无法比较"/空白/报错

### AC-3 翻月时环比与合计一起变

**当** 用户点「上一月」
**那么** 合计与环比**同时**变成那个月的数字（两者的区间口径必须同源）

### AC-4 本月没有记账时不显示环比

**给定** 本月与上月都没有记账
**当** 用户打开该月
**那么** 只显示空月的话（已有），**不再叠一句"与上月持平"** —— 没有数据的月份谈不上比较

## 业务规则

- **BR-1 口径同源**：两个月的区间都由内核 `YearMonth.toTimeRange(zone)` 算。
  与合计、占比、下钻是**同一个函数** —— 环比与合计并排显示，口径不一致就是错的。
- **BR-2 差额是 `SignedMoney`**：可以为负（与结余同一个类型与理由）。
  它**不是** `Money`：`Money` 的非负性是刻意的，不能为了一个派生量把它放开。
- **BR-3 差额由模型算，界面不算**：界面只负责选择"多花/少花/持平"的说法。
  在界面里做减法意味着两处口径（`REQ-005` 的占比就是这么做对的）。
- **BR-4 读失败时不显示假的 0**：任何一段区间读不出来，就**不显示环比**
  （沿用 `REQ-006/AC-2`：读失败说读的事，绝不拿 0 冒充"没有变化"）。
- **BR-5 不新端口**：跨上下文那个端口的 `totalsIn` 已经收任意区间 ——
  加端口等于把"同一件事"包装成两层（`ADR-0008` 的推理）。
