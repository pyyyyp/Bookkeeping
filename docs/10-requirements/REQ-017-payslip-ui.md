# REQ-017 工资单界面

- 状态: 待实现
- 优先级: P1
- 上下文: Payroll（presentation）+ `:app`（第三个页面）
- 提出: 2026-10-03
- 前置: `REQ-013`（日收入计算）、`REQ-015`（与出勤的集成）、`Q-019`（月薪带生效日期）

## 用户故事

链条已经全通了 —— 日历知道哪天是什么日子、工时知道干了多久、薪资知道该给多少 ——
**但我打开 App 还是看不到这个月该拿多少** ✗。

而且还有个更前置的问题：**月薪从来没地方配** ✗。没有它，工资单算不出来。

## 背景

`REQ-013` 把"可解释"写进了验收标准：拿到工资条那天，我要能一眼看出**每一个数字是怎么来的**。
所以这个界面不能只显示一个合计 —— 它必须显示**逐日**的判断：
哪天是工作日 `1×`、哪天是休息日加班 `2×`、哪天是法定节假日休息也带薪 `1×`、哪天是 `0`。

另一件必须说清的事：**"日收入之和 ≠ 月薪"是预期的**（`Q-015` 定案时就写明了）。
`21.75 = (365−104)÷12` 是**年平均值**，而任意单月的实际工作/休息天数都不可能正好是它。
界面要把差额显示出来并**解释一句**，而不是让用户以为算错了。

## 范围

**做**

- **配月薪**（金额 + 生效日期）并存得住 —— 涨薪是**新增一份**，不是改旧的（`Q-019`）
- 显示某个月的工资单：月薪 / 日薪 / 应付合计 / **与月薪的差额**
- **逐日明细**（每天一行：日期 / 日期类型 / 倍率 / 金额）
- 翻月（**未来月份禁用** —— 算不出未来的工资单）
- 节假日数据没填时**明说**（`REQ-012/AC-4` 的 `missingYear`）

**不做**

- 多份工作（`Q-004` 还在；表结构支持多份，界面先只配"当前那份"）
- 半天加班的倍率（`Q-025`，需要有理数倍率）
- 导出工资单 / 分享
- 编辑历史月薪（涨薪 = 新增一份，历史不改 —— 这是 `Q-019` 的决定，不是缺口）

## 验收标准

### AC-1 配置月薪并存得住

**当** 用户填金额与生效日期并保存
**那么** 它被存下来；重启 App 后仍在
**并且**它只对**生效日期之后**的月份生效（涨薪不改历史月份的工资）

### AC-2 显示某个月的工资单

**当** 打开工资单页
**那么** 看到该月的：月薪、日薪、应付合计、**与月薪的差额**
—— 差额**如实显示**（可以不为零，也可以为负），不硬凑（`REQ-013/AC-5`）

### AC-3 逐日明细

**当** 往下看
**那么** 该月每一天都有一行：日期 / 日期类型 / 倍率 / 金额
—— **不做折叠**（`Q-029`）：31 行在滚动列表里不是负担，而"为什么是这个数"正是这个页面的意义

### AC-4 差额要有一句解释

**那么** 界面上说明差额的来源：`21.75` 是**年平均值**，所以单月的日收入之和不会正好等于月薪
—— 不解释的话，用户会以为算错了（这是"可解释"的一部分，不是装饰）

### AC-5 未来月份禁用

**当** 当前就在本月
**那么** 「下一月」**禁用**（不是点了没反应）—— 未来的工资单算不出来
（与 `MonthlyTotalsUiState.canGoToNextMonth` 同一条规则）

### AC-6 节假日数据没填时明说

**那么** 工资单上带出「这一年还没有节假日数据，节假日按周末规则推定」
—— 否则用户会以为今年没有节假日（`REQ-012/AC-4`、`REQ-015/AC-6` 的同一原则）

## 业务规则

- **BR-1 界面不做算术**：合计、差额、倍率全由 `Payslip` 给出（`REQ-013/BR-*`）。
  界面只负责显示与布局 —— 在界面里做减法就是第二处口径。
- **BR-2 没有月薪时不算**：`effectiveAt` 返回空 → 显示"先配月薪"，而不是按 0 算。
  用 0 算会得到一份看起来正常、实际全错的工资单。
- **BR-3 算到哪一天**：当月算到**今天**（`REQ-015/AC-5`），已过去的月份算到**月末**。
- **BR-4 页面的月份**由界面自己的状态持有（与 `MonthlyTotalsViewModel` 同一条做法）。
