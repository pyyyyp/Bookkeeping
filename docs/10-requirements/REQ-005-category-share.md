# REQ-005 分类占比

- 状态: 待实现（**阶段 B / C 已完成**：需求 + 任务卡；实现见 `T-013`）
- 上下文: Insight（读模型）
- 提出: 用户（2026-10-02，在 `REQ-004` 完成后的候选里选了本项）
- 关联: `ADR-0008`（跨上下文读通路）、`ADR-0009`（分类归档）、`REQ-002`（本月合计）、`REQ-004`（自定义分类）

## 用户故事

> 作为一个每月都在记账的人，
> 我想看到「这个月的钱花在哪了」——按分类排出金额与占比，
> 这样我能看出哪一类在吃掉我的收入，而不是只看到一个总数。

## 范围

**做**：

- 在合计区下面给出本月**支出**按分类的清单：分类名 + 金额 + 占比（保留 1 位小数）
- 按金额**降序**；金额相同时按分类名（结果与数据来源无关，可复现）
- 跟着合计区**同一个月份**切换（翻月一起变）
- **已归档的分类照样计入并显示**（见 `BR-2`）
- 没有支出时给出空状态（而不是 `0 / 0` 这种算式）

**不做**（写清楚，避免"顺手加"）：

- **收入占比**（`BR-1`）：收入通常只有一两类，"工资占 100%" 没有信息量
- 环形图 / 饼图 / 动画（视觉设计未定，`Q-020`；先用文字 + 一个简单的比例条）
- 点分类下钻到条目列表（那是另一个需求：需要按分类查条目）
- 同比 / 环比 / 趋势（需要跨月比较，`REQ-006` 候选）
- 自定义时间范围（现在只有"月"这一种口径）
- 导出 / 截图

## 验收标准

> 业务语言，不提技术实现。AC 编号一旦分配不复用。
> ⚠️ 格式必须是 `### AC-n <标题>`（追溯脚本按这个模式抓取）。

### AC-1 看到本月支出按分类的清单

```
Given 本月我记了几笔支出，分属不同分类
When  我打开记账页
Then  合计区下面按分类列出：分类名、金额、占比
      例如「餐饮 ¥120.00 60.0%」
```

### AC-2 金额大的排在前面

```
Given 本月「餐饮」花了 120 元、「交通」花了 30 元
When  我看占比清单
Then  「餐饮」在「交通」前面
```

### AC-3 占比各自四舍五入，不强行凑成 100%

```
Given 本月支出分属三类，金额各占三分之一
When  我看占比清单
Then  三行各显示 33.3%
      （加起来 99.9% 是**正确的**：为了凑满 100% 而改动某一类的数字，等于让明细对不上金额）
```

### AC-4 已归档的分类仍出现在清单里

```
Given 分类「宠物」已被归档，但本月有一笔账用的是它
When  我看占比清单
Then  「宠物」照常出现在清单里并计入合计
      （把它排除会让"各分类之和 ≠ 支出合计"，用户会认为账算错了）
```

### AC-5 没有支出时给空状态

```
Given 本月没有任何支出
When  我看占比清单
Then  显示"本月还没有支出"之类的空状态
      而不是 0 元 / 0.0%（那会让人以为哪里算错了）
```

### AC-6 跨月补记的条目不会进本月清单

```
Given 我在 10 月补记了一笔发生时间是 9 月的支出
When  我看 10 月的占比清单
Then  那笔**不在** 10 月清单里；翻到 9 月才看得到
      （口径与合计一致：按发生时间归属）
```

### AC-7 翻月时清单与合计一起变

```
Given 我在看 10 月的合计与占比
When  我点「上一月」
Then  合计与占比清单**同时**变成 9 月的数据
      （不允许一个变了另一个没变——那会让人对着两个月的数字算账）
```

### AC-8 收入不进入占比清单

```
Given 本月有一笔 8000 元的工资收入
When  我看占比清单
Then  清单里**没有**它，占比的分母也只是支出合计
```

## 业务规则

| 编号 | 规则 | 理由 |
|---|---|---|
| `BR-1` | v1 **只做支出占比**，分母是支出合计 | 收入通常只有一两类，"工资占 100%" 没有信息量；混在一起算更没意义（收入与支出不是同一个池子） |
| `BR-2` | **已归档的分类照样计入并显示名字**（`ADR-0009`） | 排除它会让各分类之和 ≠ 支出合计 —— 用户会认为账算错了。归档的含义是"记账时别再让我选它"，不是"从历史里抹掉" |
| `BR-3` | 占比 = 该分类金额 ÷ 支出合计，**各自四舍五入到 1 位小数**；总和**不保证**是 100% | 强行凑百必须篡改某一类的数字，那比"99.9%"糟得多 |
| `BR-4` | 排序：金额**降序**，金额相同按**分类名**升序 | 金额相同也要有确定顺序，否则同一份数据两次渲染可能不同（测试也会变得不稳定） |
| `BR-5` | 口径与合计**完全一致**：按条目的**发生时间**归属到月，半开区间 `[start, end)` | 两个数字并排出现在同一屏上，口径不一致就是错的（`REQ-002/BR-2` 的同一要求） |
| `BR-6` | 支出合计为 0 时返回**空清单**（不是每类 0%，也不是错误） | "没有支出"是正常状态；避免除零（`REQ-002` 对"没有记账"的同一处理） |
| `BR-7` | 分类名由 **Ledger** 解析后传给 Insight（Insight 不拥有分类语义） | Insight 是读模型，按 R2 它也看不见 Ledger 的分类模型。契约在内核（`ADR-0008`），传的是"给人看的名字 + 金额" |
