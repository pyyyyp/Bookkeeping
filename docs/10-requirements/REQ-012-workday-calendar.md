# REQ-012 工作日历：判定某一天是什么日子

- 状态: 待实现
- 优先级: P1
- 上下文: Calendar（支撑域）
- 提出: 2026-10-03
- 前置: `Q-015`、`Q-016`（均已定案，见 `open-questions.md`）、`ADR-0011`
- 下游: Payroll（日收入倍数）、Worklog（哪天算加班）

## 用户故事

工资是按天算的，而"某天是什么日子"决定倍数（工作日 1× / 休息日加班 2× / 法定节假日加班 3×）。
所以在我能算工资之前，得先有一个**权威的**地方回答："2026-10-01 是什么日子？"

## 背景

这件事**看起来**只是查表，其实有三个坑：

1. **调休**：国庆前后那个周六是**工作日**。按星期几判会判错，而判错的代价是钱。
2. **数据是外部的、一年一换**：由国务院发布。它必须被隔离在一个上下文里（`ADR-0011`）。
3. **数据可能还没有**：某一年没填时若静默按周末判，用户会以为"今年没有节假日" ——
   而真相是"数据还没有"。**这两件事必须能区分。**

## 范围

**做**

- 判定某一天的 `DayType`（工作日 / 休息日 / 法定节假日）
- 调休优先于星期几
- 覆盖表里的显式标注优先于任何推导（含把工作日标成休息）
- 数据缺失/损坏时：退化为周末规则 + **显式告知**（`missingYear`）+ 记日志

**不做**

- 界面（v1 不做日历页；`T-025` 只交付能力）
- 「用户手动标记某天」（数据层支持覆盖，界面不做）
- 工作日天数统计、加班时长（那是 Worklog / Payroll 的事）
- **填写真实的 2026 年节假日日期**：那是现实世界的事实，凭记忆编就是猜（P5）。
  机制交付后，填数据是**每年一次的手工步骤**

## 验收标准

### AC-1 判定某一天的日期类型

**给定** 该年的节假日数据里 `2026-10-01` 是法定节假日
**当** 询问这一天的类型
**那么** 返回 `STATUTORY_HOLIDAY`，且 `missingYear = false`

### AC-2 调休：被调成工作日的周六判为工作日

**给定** 数据里某个周六被标为工作日（调休）
**当** 询问那一天
**那么** 返回 `WORKDAY`（**不是** `REST_DAY`）—— 星期几与日期类型不一致时，以日期类型为准

### AC-3 普通周六周日是休息日

**给定** 该年有数据，且某周六没有任何标注
**当** 询问那一天
**那么** 返回 `REST_DAY`

### AC-4 数据缺失的那一年：退化 + 显式告知

**给定** 该年**没有**节假日数据
**当** 询问这一年里的任何一天
**那么** 按周末规则给出类型，**并且** `missingYear = true`
（调用方能据此提示一次，而不是让用户以为"今年没有节假日"）

### AC-5 坏数据不影响可用性

**给定** 节假日数据文件损坏（JSON 解析失败）
**当** 询问任何一天
**那么** 当作该年无数据（`missingYear = true`）+ 记一条日志，**不抛异常、不崩**

## 业务规则

- **BR-1 只有 Calendar 能判定日期类型**：它由国务院发布的节假日与调休安排决定，
  是外部事实，不是各上下文各自解释的东西。类型住共享内核以便传递，**所有权仍在这里**（`ADR-0011` 决策 4）。
- **BR-2 覆盖优先于推导**：顺序是「覆盖表 → 周末规则」。反过来会让调休判错。
- **BR-3 外部格式绝不进领域层**（`R6`）：JSON 经 Mapper 变成领域类型。
- **BR-4 缺失与"没有节假日"必须区分**：`missingYear` 是这条规则的载体。静默退化最糟。
- **BR-5 纯查询、无事件**：同步只读（`Conformist`）。把"今天是工作日吗"变成异步通知，
  是把最简单的问题复杂化。
- **BR-6 判定是纯函数**：数据进、类型出。没有聚合，因为没有需要守住的不变式。
