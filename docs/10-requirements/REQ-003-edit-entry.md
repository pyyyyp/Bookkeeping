# REQ-003 编辑已保存的条目

- 状态: 待实现（**阶段 B / C 已完成**：需求 + 模型补充 + 任务卡；实现见 `T-011`）
- 上下文: Ledger
- 提出: 用户（2026-10-02，在 `REQ-002` 完成后的候选里选了「编辑已保存的条目」）
- 关联: `REQ-001`（记一笔 / 列表 / 删除）、`REQ-002`（本月合计）、`ADR-0005`（v1 范围）

## 用户故事

> 作为一个记账的人，
> 我想把已经记下的那条改一改（金额输错了、分类选错了、日期选错了），
> 这样我不必先删掉再重新记一遍——尤其是那笔账的其他字段都是对的。

## 范围

**做**：

- 列表里每条记录有**编辑**入口；点开后**表单载入该条目的现有值**（含发生时间）
- 保存后**替换**那条记录（条目数量不变，不是新增一条）
- 编辑时可以改：金额、收支方向、分类、发生时间、备注
- **领域规则照旧生效**：金额必须大于 0、必须选分类、备注不超 200 字（`REQ-001/AC-3` `AC-4` `AC-6`）
- 编辑**可以取消**；取消后原条目一字不变
- 编辑成功后，本月合计**立即**跟着变（`REQ-002/AC-4` 的同一机制）
- 编辑后重启应用，改动仍在

**不做**（写清楚，避免"顺手加"）：

- 编辑**录入时间**（见 `BR-3`）与条目身份
- 撤销 / 编辑历史 / 审计轨迹——**没有"撤销编辑"这个功能**，改错了只能再改一次或删掉
- 批量编辑、跨条目移动（例如把这条的金额挪到另一条）
- 编辑分类定义本身（那是"自定义分类"，另一个需求）
- 编辑已删除的条目（它已经不在账本里了，见 `BR-5`）

## 验收标准

> 业务语言，不提技术实现。AC 编号一旦分配不复用。
> ⚠️ 格式必须是 `### AC-n <标题>`：追溯校验脚本按这个模式抓取（`scripts/verify-traceability.ps1` 规则 2）。

### AC-1 改金额与分类后替换原条目

```
Given 账本里有一条「支出 12.50 餐饮 2026-10-02」
When  我点它的编辑入口，把金额改成 20.00、分类改成「交通」，然后保存
Then  列表里那条显示「支出 20.00 交通 2026-10-02」
      并且账本里**仍然只有一条**（不是新增一条、也不是两条并存）
```

### AC-2 可以修改发生时间

```
Given 我 10-02 补记了一笔，但发生时间误选成 10-02（本应是 09-15）
When  我编辑它，把发生时间改成 2026-09-15 并保存
Then  该条的发生时间变为 09-15
      并且它从此计入 **9 月**的合计（而不是 10 月）
```

### AC-3 编辑时领域规则照旧生效

```
Given 我在编辑一条支出
When  我把金额清空（或填 0）、或把分类取消选择、或备注写到 201 个字，然后保存
Then  界面给出对应的提示（与记一笔时同样的提示）
      并且**原条目一字不变**（没有被改成半成品）
```

### AC-4 编辑不改变录入时间与条目身份

```
Given 一条 10-02 录入、发生时间为 09-15 的条目
When  我编辑它的金额并保存
Then  它的录入时间仍是 10-02（编辑不会把"什么时候记进账本"改掉）
      并且它在账本里的**身份不变**（同一条记录，不是删掉再新建一条）
```

### AC-5 编辑后本月合计立即更新

```
Given 10 月的支出合计是 ¥25.00，其中包含一条 ¥10.00
When  我把那条改成 ¥30.00 并保存
Then  10 月的支出合计立刻变成 ¥45.00，不需要切界面或重开 App
```

### AC-6 取消编辑不改变任何东西

```
Given 我在编辑一条 ¥12.50 的支出，已经把它改成 ¥99.00
When  我点取消
Then  账本里那条仍是 ¥12.50，什么都没变
```

### AC-7 编辑后重启仍在

```
Given 我把一条支出从 ¥12.50 改成 ¥20.00 并保存成功
When  我彻底关掉应用再打开
Then  那条仍是 ¥20.00
```

### AC-8 编辑一条已经不存在的条目时给出明确结果

```
Given 我打开编辑界面后，那条记录在别处被删掉了（例如另一处操作）
When  我点保存
Then  界面明确告诉我这条已经不在了，而不是假装保存成功
      并且不会因此凭空造出一条新记录
```

## 业务规则

| 编号 | 规则 | 理由 |
|---|---|---|
| `BR-1` | 编辑是**整条替换**：保存后那条记录的可编辑字段全部取表单当前值 | 界面就是那张表单；"只提交变了的字段"会引入两套真相 |
| `BR-2` | 编辑**可以修改发生时间** | ✅ **已定案**（2026-10-02）：这个功能最主要的用例就是"补记时日期选错"。`ADR-0005` 的 v1 没有账户、没有结算周期，也就没有会把条目"冻结"的下游约束；将来若有（例如条目已并入工资单），那时再加"不可编辑"的规则并记 ADR |
| `BR-3` | 编辑**不改变**录入时间（`bookedAt`） | 录入时间回答的是"这笔什么时候被记进账本"，那是一个**已经发生的事实**，不会因为后来改了内容而改变。否则它将不再有信息量 |
| `BR-4` | 编辑**不改变**条目身份（`LedgerEntryId`） | 它就是"同一条记录"。若换了 id，等于删一条加一条——`REQ-001/AC-4` 的意义也就没了 |
| `BR-5` | 编辑一条**已不存在**的条目时返回"条目不存在"，**不新建** | 与删除一致的"影响行数为 0"语义；悄悄插入会让用户以为改动生效了 |
| `BR-6` | 编辑与记账共用**同一套**领域校验 | 两条路径各写一遍校验，迟早会漂移（其中一条会漏掉后来新增的规则） |
| `BR-7` | 编辑成功后本月合计**立即**重算 | 与 `REQ-002/AC-4` 同源：合计靠"数据修订号"驱动，改动必须计入 |
| `BR-8` | 没有"撤销编辑" | 这是 v1 的取舍：`ADR-0005` 的物理删除已经意味着"改动不可追溯"，编辑沿用同一立场。真要做审计轨迹，那是一个新需求 + 新 ADR |
