# ADR-0009 分类的生命周期：归档，而不是删除

- 状态: **已接受**（2026-10-02）
- 决策者: 用户（选择需求）+ Agent（方案）
- 关联: `REQ-004`、`ADR-0005`（v1 范围：预置分类只读）、`ADR-0007`（数据层归属）

## 背景

`REQ-004` 让用户能自己建分类。随之而来的第一个问题是：
**一个已经被历史条目引用的分类，用户想"删掉"它时该怎么办？**

条目存的是**分类 id**（不是名字），所以有三种可能：

| 方案 | 后果 |
|---|---|
| A. 物理删除分类 | 历史条目指向一个不存在的 id → 要么显示空白（历史变得看不懂），要么得**改写**那些条目 |
| B. 拒绝删除 | 安全，但用户只是想让"宠物"别再出现在选择器里，却被告知"请先改掉 87 条账" |
| C. 归档（记一个 `archived` 状态） | 选择器里不再出现，历史条目照旧显示它的名字 |

## 决策

**采用 C：分类只有"归档 / 恢复"，没有物理删除。**

- `archived` 是分类自己的状态（同一聚合内）✓
- 归档的分类**不出现在记账选择器**，但**仍能被解析出名字**（历史渲染照旧）✓
- 归档可撤销 ✓
- **预置分类只读**（`BR-2`）：不可改名、不可归档 —— 内置内容与用户内容是两种东西

另外两条由此派生：

- **唯一性检查放在应用层**（`BR-7`）："所有分类里不能重名"是跨聚合规则，
  放进 `Category.init` 会得到一个聚合内无法验证的规则。
- **条目继续只存分类 id**（`BR-6`）：所以重命名天然不会碰任何条目，
  而"改名后历史跟着变"是免费的 —— 这正是当初存 id 的价值。

## 被否方案

### A. 物理删除（含"删除时把引用改到『其他』")

- 为什么否掉：把引用改到 `其他` 是**改写历史** —— 用户过去的某笔"宠物"支出变成了"其他"，
  而账本的意义就是忠实记录。物理删除 + 悬空引用更糟：历史变得看不懂。
- 与 `ADR-0005` 的关系：那里选了**条目**的物理删除，因为条目没有下游引用者；
  分类**有**（被条目引用）。同一个词在不同聚合上结论不同，这不是矛盾，是边界。

### B. 拒绝删除（要求先改掉所有引用）

- 为什么否掉：把清理成本推给用户，而他的目标只是"别再让我选到它"。
  归档用一次点击达成同一个目标，且不损失任何历史。

### 预置分类也允许改名/归档

- 暂不做：会让"恢复默认"变得含糊（用户改了「餐饮」，谁记得原来叫什么）。
  要做的话应当先定"默认值从哪里来"，那是另一个需求。

## 影响

- **数据库多一张表**（`category`）→ Room `version` 1 → 2，**必须写迁移**，
  且**禁止** `fallbackToDestructiveMigration`（禁令 14）。升级不能清空用户已有的账 ✓
  （`REQ-004/AC-9` 会在模拟器上用**真实历史数据**验证这次迁移）
- 预置分类**继续写在代码里**（`CategoryCatalog`），只在读取时与库里的自定义分类合并。
  这样迁移不需要"塞初始数据"，也不存在"预置分类被误删"的可能
- `Category` 从**值对象**升级为**聚合根**（有标识、有生命周期、有归档状态）——
  这正是它在 `T-007` 时留下的那句话所预告的
- `CategoryCatalog.PRESET` 的用途收窄：它变成"内置分类的定义"，而**界面要用的分类清单**
  改由用例提供（预置 ∪ 未归档的自定义）

## 复审条件

1. 出现"预置分类也要能改"的真实需求 → 先定"默认值从哪来"，再改本决策；
2. 分类数量大到需要分页/搜索（目前是几十个量级）→ 那时再谈；
3. 出现"合并两个分类"的需求 → 那必然涉及改写历史，是另一个决策 + 新 ADR。
