# ADR-0011 工作日历：日期类型、节假日数据源，以及它与上下文地图的一处冲突

- 状态: **已接受**（2026-10-03）
- 相关: `Q-015`、`Q-016`、`REQ-012`、`T-025`、`ADR-0008`（跨上下文读模型）、`ADR-0009`（判例：谁能定义什么）

## 背景

Payroll 要算「某天的日收入」，而"某天是什么日子"决定了倍数：

```
工作日          → 1 × 日薪
休息日  加班    → 2 × 日薪
法定节假日 加班 → 3 × 日薪
休息日  不加班  → 0
```

所以先得有一个东西能回答「2026-10-01 是什么日子」。它由国务院每年发布的
**法定节假日与调休安排**决定，而且会调整（某个周六可能被调成工作日）。

`Q-016` 问的就是这件事：数据从哪来、怎么更新。

## 决策

### 1. 数据源：内置**行式文本** + 每年手动更新（否决第三方 API）

- **选 (a) 内置数据文件**：与"离线优先、Room 是唯一事实源"一致（`ADR-0001`）。
  一年一次的手动更新，换来的是**没有任何运行时网络依赖**。
- 否决 (b) 第三方 API：把一个**一年变一次**的数据变成网络依赖，还得处理超时/缓存/字段变更 ——
  成本与风险都远大于它省下的那一次手工。
- 否决 (c) 只在界面上让用户手动标记：那会把"法定"变成"自定"，工资的口径就不再可解释。

**格式：行式文本，不用 JSON**（本 ADR 初稿写的是 JSON，落地时改了 —— 理由如下）：

本仓库**没有 JSON 依赖**（`ADR-0001` 的选型里没有序列化库），
而为了这份数据引入一个依赖，属于"新依赖必须先问"的阻塞项；同时：

| 理由 | 说明 |
|---|---|
| 形状不匹配 | 这份数据就是"一列日期 + 一个词"。JSON 的嵌套与转义在这里**什么也没换来** |
| `git diff` 可读 | 一年一次的更新，最重要的就是**一眼看出哪一天改了**。行式文本做到了，JSON 做不到 |
| 能写注释 | 数据里要写清"来源：国务院 X 年公告" —— 行式文本支持注释，JSON 不支持 |
| **可纯 Kotlin 解析** | 因此**不需要 Robolectric 就能单测**（`org.json` 是 Android 类，在纯 JVM 测试里会抛 "not mocked"） |

格式（`feature:calendar` 的 assets，文件名 `holiday_data.txt`）：

```
# 每年更新一次：国务院发布后填写。空行与 # 开头是注释。
# 格式：<yyyy-MM-dd> <holiday|workday>
#   holiday = 法定节假日，workday = 调休（被调成工作日的周末）
2026-10-01 holiday
2026-10-10 workday
```

**没有 `year` 声明行**（初稿有，落地时删了）：**日期自带年份**，
再写一行"我在声明 2026 年"只会制造一个陷阱 —— 那行与真实数据不一致时谁说了算？
于是规则简化成一句：

> **某一年有数据 ⇔ 该年至少有一条日期行。**

**坏行**：跳过该行 + 计数 + 记日志（一行坏不毁掉一整年）；
**整份数据读不出来** → 所有年份都视为无数据（见决策 2）。

> ⚠️ 一个**明说**的局限：这个定义只能分辨"整年没数据"与"有数据"，
> 分辨不了"这一年只填了一半"。后者是**维护者的责任**，不是解析器的 ——
> 假装能自动发现它，反而会让真正该修数据的人以为程序会提醒他。

### 2. 数据缺失时的行为：**退化成周末规则，并且说出来**

数据是**按年**的。若某一年还没填：

- 判定退化为「周六周日 = 休息日，其余 = 工作日」；
- **必须让调用方知道**（返回值里带一个"这一年没有数据"的标志），界面据此提示一次。
  **静默退化最糟**：用户会以为"今年没有节假日"，而真相是"今年的数据还没填"。

> 同理，数据**格式不对**（坏 JSON / 日期解析失败）→ 当作"这一年没有数据"并记日志，
> 不让整个 App 因为一份附带数据而崩。

### 3. 覆盖优先于周末规则

判定顺序：**覆盖表 → 周末规则**。

- 覆盖表把某个日期显式标成工作日（**调休**，例如国庆后的那个周六）或法定节假日；
- 没有覆盖的日期才按星期几判。
- 覆盖表还允许把某个工作日标成休息（`Q-016` 建议里的"允许用户覆盖单日"）——
  数据层支持，界面 v1 不做。

### 4. ⚠️ 与上下文地图的一处冲突（显式说明，不静默取舍）

上下文地图写着：

> **`DayType` 不放共享内核** —— 它是 Calendar 的概念，Payroll 通过 Calendar 的只读接口获取，
> 不得自己定义一份。

按 §0 的优先级：`R2`（feature 之间不得互相依赖，第 4 节）**高于**本文件其余章节（第 9 节）。
而"Payroll 通过 Calendar 的只读接口获取"若按字面做，就是 `feature:payroll → feature:calendar`，
**直接违反 R2**。

**裁决**（沿用 `ADR-0008` 已立的先例，与 `LedgerTotalsReader` 完全同构）：

| 东西 | 放哪 | 为什么 |
|---|---|---|
| `DayType`（值对象） | **`core:domain`** | 它必须跨上下文传递。内核里已有同类先例：`MonthlyTotals`、`CategoryBreakdown` 都是"语义归某个上下文、类型放内核" |
| `WorkCalendar`（只读端口） | **`core:domain`** | 消费方是 Payroll，实现在 Calendar —— 读通路住内核、实现住上下文、装配在 `:app`（`ADR-0008`） |
| 判定规则与实现 | `feature:calendar` | 「哪一天是什么日子」**只有 Calendar 说了算** |
| 节假日 JSON | `feature:calendar`（外部格式，绝不进内核） | `R6`：外部模型必须经 Mapper |

**因此上下文地图那句话改为**：`DayType` 的**语义**归 Calendar，
**类型**放共享内核（跨上下文传递的需要），**任何其他上下文不得重新定义一份**。
—— 这不是放宽约束，而是把"谁能定义"从一个**位置**问题改成**所有权**问题；
先例是 `ADR-0008`：`MonthlyTotals` 也住在内核，而"哪个月的合计"只有 Ledger 说了算。

### 5. 不引入领域事件

Calendar 是**只读的日期查询**（`Conformist`：Payroll 顺从 Calendar 的定义，见上下文地图）。
本地数据、同步查询，不需要事件 —— 引入事件会让"今天是工作日吗"变成一个异步问题，
而那正是最不该异步的地方。

## 影响

- 新增 `core:domain`：`DayType`、`DayKindResult`（判定结果 + 数据缺失标志）、`WorkCalendar` 端口
- 新增 `feature:calendar`：判定规则、JSON 解析与 Mapper、端口实现
- `:app`：装配（Hilt）
- 未决：`Q-015` 的规则（缺勤/节假日带薪）已按建议默认值定案，见 `open-questions.md`

## 被否方案

| 方案 | 否决理由 |
|---|---|
| 第三方 API | 把一年一次的数据变成网络依赖（见决策 1） |
| 把 `DayType` 定义在 `feature:calendar`，Payroll 直接依赖它 | 违反 `R2`。若为此放宽 R2，代价是"上下文边界"不再是可检查的事实 |
| 把节假日数据放进内核 | `R6`：外部格式不进领域层；而且内核应当越小越好 |
| 数据缺失时静默按周末规则 | 用户会以为"今年没有节假日"（见决策 2） |
