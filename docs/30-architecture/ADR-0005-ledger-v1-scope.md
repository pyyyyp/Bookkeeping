# ADR-0005 Ledger v1 的范围决策（不做账户、不做多币种、物理删除、预置分类）

- 状态: **已接受**（用户 2026-10-02 就四项范围逐条选定）
- 日期: 2026-10-02
- 决策者: 用户 + Agent
- 相关: `REQ-001`、`Q-005`（本 ADR 关闭它）、`Q-008`、`Q-021`、`docs/20-domain/ledger-model.md`

> ADR **只追加不改写**。本 ADR 记录 Ledger 第一个切片（`REQ-001`）的范围取舍，
> 目的是让「为什么现在不做账户」这类问题**不需要重新讨论一遍**，
> 同时把每一项的**反转成本**写清楚——因为「以后再加」的成本正是这些决策的依据。

## 背景

第一个业务需求选了 Ledger 的手动记账。它是唯一不被未决问题阻塞的端到端路径
（`Q-015` 卡 Payroll、`Q-016` 卡 Calendar），但它自己带着一个 🟡 未决问题
（`Q-005`：是否要多账户与多币种），以及若干会显著改变模型与工作量的范围选择。

按 `AGENTS.md` 第 10 节，范围与「涉及用户数据」的选择必须由用户拍板；
四项已逐条确认，本文记录**理由与后果**，避免下一轮重新论证。

## 决策

### 1. v1 不做账户（`Account` 不进 `LedgerEntry`）

- `LedgerEntry` 的字段就是：方向、金额、分类、发生时间、录入时间、备注。
- 术语表中的 `Account` 词条标记为**「已延后，v1 不使用」**，不删除——
  它是已识别的领域概念，删掉反而会让人以为没想到。

**理由**

| 取舍 | 说明 |
|---|---|
| 账户的最小形态其实很便宜（一个标签字段） | 但「记账时选账户」会立刻带出「账户从哪来 / 能不能增删改 / 余额怎么算」——那是另一个需求，不是本卡的副产品 |
| 本卡要验证的是**端到端链路能不能通**（domain → data → UI → DI） | 每多一个概念，就多一份在链路还没跑通前就要维护的模型 |
| **反转成本低** | 加账户 = 加一个**可空**字段 + 一次 Room 迁移；历史条目的账户为 `null`，语义是「未指定」，不是「未知的钱」 |

### 2. 不做多币种

`Money` 以「分」为单位且不带币种。理由：单人自用、记账范围不含外币；
多币种会污染共享内核（`Money` 属于 `core:domain`，改动需要跨上下文确认 + ADR），
为一个尚未出现的需求付这个代价不划算。**反转成本高**（要改共享内核），
所以这里明确写下：**真要做多币种时，必须新开 ADR，不能顺手加个字段。**

### 3. 删除是**物理删除**，二次确认后不可恢复

**理由**

- 个人记账**没有审计要求**：软删除会往「唯一事实源」里塞进用户看不见的行，
  之后每一条查询、每一个统计都要记得过滤它——这个代价是**长期且弥漫**的。
- 被否方案：**软删除**（`deletedAt` 列 + 全局过滤）。否掉的理由同上；
  它的唯一好处（可恢复）可以用更直接的方式获得。
- 被否方案：**撤销窗口**（删除后 5 秒内可撤销）。否掉的理由是它会引入
  「已提交但可能被撤回」的中间状态，而本卡还没有任何需要处理中间状态的地方。
- **反转成本中等**：改成软删除要加列 + 迁移 + 全查询过滤；
  由于数据库是本机 SSOT 且用户是唯一使用者，将来真要做也有明确的迁移路径。

**用户可见行为**：确认删除后条目从列表消失，重启也不回来（`REQ-001` AC-9）。

### 4. 分类为**预置、只读**，自定义分类另开一张卡

- 预置清单放在**领域层**（`Category` 值对象 + 一张清单表），不是 UI 层的下拉数据——
  「有哪些分类」影响条目的合法性与后续统计口径，是业务内容。
- 本卡 `Category` 是**值对象**；等自定义分类落地时，它很可能要升级为聚合
  （「同名不可重复」「被引用的分类不可删」是跨条目的一致性要求）。
  **那时需要新的 ADR**，本卡不预设。

### 5. 本卡不引入领域事件

领域事件是**跨上下文**解耦的通道。本卡没有任何订阅方：
Insight 是只读投影（直接读库），Payroll → Ledger 的事件要等 Payroll 落地。
**没有订阅方的事件是投机性抽象**，等真实订阅方出现再加。

## 后果

| 后果 | 影响 |
|---|---|
| `LedgerEntry` 的字段数保持最小（6 个） | 数据层与 UI 都简单，本卡的验收面可控 |
| 没有账户 ⇒ **没有「余额」这个概念**，也没有任何跨条目的一致性 | 这直接支撑了「条目即聚合根」的建模（见 `ledger-model.md`） |
| 删除不可恢复 | 用户必须靠二次确认避免误删；将来若要「撤销」，按上文反转成本另开 ADR |
| 分类不可自定义 | 预置清单不满足需求时，用户会**立刻**提出来——这比我们先猜一套可编辑分类更省事 |

## 被否方案汇总

| 方案 | 否掉的理由 |
|---|---|
| v1 就做账户（含余额/转账） | 远超第一个切片；且余额会引入跨条目不变式，等于先建一个大聚合 |
| 账户只当纯标签 | 不是错的，但会带出「账户从哪来」，仍然是一个独立需求 |
| 软删除 / 撤销窗口 | 长期弥漫的过滤成本 vs 一个可以更直接解决的「可恢复」需求 |
| 完全自定义分类 | 第一次使用必须先建分类才能记账，且要处理重名与孤儿引用 |
| 只做支出（不做收入） | `EntryDirection` 已是领域核心概念，且「收入怎么记」绕不开（工资单最终就是一笔收入） |

## 未决

- `Q-021`（本轮新增）：是否允许记录**未来时间**的账——本卡不校验，也不写成业务规则
